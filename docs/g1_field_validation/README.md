## 1. 先把几个容易混淆的问题说清楚

- **Arm SDK 不要求腿正在走。** 本地官方《高层运动开发》PDF 第 4 页明确说明：
  该接口由内置运动服务提供，无需进入调试模式，测试建议悬挂并进入锁定站立模式。
  因此先做悬挂静态控臂有官方依据；但目标固件是否确实接受，仍需验证。[S1]
- **本路线不进入 debug，不调用 `ReleaseMode()`。** 我们要保留内置平衡／行走。
  官方 XR 协同路线也这样区分；不能把低层开发的 debug 要求套到这里。[S3]
- **你看到的过程基本符合官方的状态区别。** “零力矩 → 阻尼 → 摆出准备站姿但
  不平衡 → 内置运控平衡／行走”有资料依据。第三步叫“预备／锁定站立”，
  不等于运控中的自主平衡站立。看到腿伸直，不能据此撤掉支撑。[S2]
- **不要把原地踏步设为必做动作。** 较新的本地《操作指南》PDF 第 3 页把常规运控
  的“持续踏步”标为“不推荐”。先验证自主平衡站立时控臂，再由带教按目标固件
  选择允许的踏步，或受保护的短距离慢走；不为了验收强开持续踏步。[S2]
- **外部电脑可以直接走 SDK2/DDS，不必先 SSH 到 PC2。** 沿用已成功读状态的有线
  路径。暂不研究教员的 SSH 脚本，但必须由带教确认 PC2、其他电脑和 App 没有另一套
  用户控臂／行走程序正在竞争控制。内置运控本身则要保留。[S3][S4]

接线与控制关系可以简单理解为：

```text
外部电脑 ── 已确认的有线开发网络 ── G1
  状态订阅       ← rt/lowstate 等：读回关节、IMU
  Loco/RPC       → 内置运控：给行走目标，腿部控制仍由机器人完成
  rt/arm_sdk     → 内置运控的上肢协同接口：给手臂目标与接管权重
```

它不是绕过内置程序的全身低层接管，也不是把仿真里的腿部策略搬上机器人。

### 官方有哪些模式：先区分“摆出站姿”和“自主平衡”

本地官方《软件服务接口》PDF 第 6 页的“模式 ID 说明”列出了以下 **10 个 FSM ID**。
这是该版官方文档的目录，不代表目标固件全部支持，也不代表所有版本只有这 10 个。[S9]

| FSM ID | 官方名称 | 对本次实验意味着什么 |
| --- | --- | --- |
| 0 | 零力矩 | 不主动支撑身体；无平衡控制 |
| 1 | 阻尼 | 有阻尼，但不自动站稳；无平衡控制 |
| 2 | 位控下蹲 | 摆出下蹲姿态；无平衡控制；本次不测 |
| 3 | 位控落座 | 摆出落座姿态；无平衡控制；本次不测 |
| 4 | 锁定站立 | 摆出准备站姿，但无平衡控制；悬挂 A2 的目标状态 |
| 500 | 常规运控 | 内置控制负责平衡／行走；本次单腰 yaw 机器的协同路线候选 |
| 501 | 常规运控-3Dof-waist | 三自由度腰版本；不作为本机的试验目标 |
| 801 | 走跑运控 | 另一套走跑控制；不把它与 500 混称，也不在本次顺带测试 |
| 706 | 平衡下蹲、蹲起 | 特定动作转换；本次不测 |
| 702 | 躺起 | 特定起身动作；本次不测 |

另外，**debug／调试模式是退出内置运控后的底层开发状态**，不在上述表中分配一个
可照抄的 `SetFsmId` 编号。本次保留内置运控与 Arm SDK，不进入 debug。[S1][S3][S9]

英文名称不是三个依次切换的档位：

- `Motion / motion control mode` 在官方 XR 说明里是“由内置运控负责下肢”的总体路线，
  不是一个统一名为 Motion 的新 FSM ID。
- `Regular mode` 对应常规运控；官方 XR 对单腰关节机器明确推荐这条协同路径，
  与上述表的 `500` 对照，而非三腰的 `501`。[S3][S9]
- 常规运控内又有“平衡站立”和“持续踏步”等行为。已经在常规运控中自主平衡站着，
  再给有限时长的非零速度目标就可请求行走，不需要先换成 `801` 才能走。[S4][S9]

因此后续落地流程是：**锁定站立 4 → 双脚触地并保留保护 → 常规运控 500 →
确认自主平衡 → 请求有限行走目标**。常规运控中“平衡站立”不是锁定站立 4：
前者会在必要时迈步维持平衡；后者没有自主平衡。[S9]

### 怎样切模式：A1 优先试电脑，不依赖未核实的遥控器按键

`Damp() → SetFsmId(1)`、`StandUp() → SetFsmId(4)`、`Start() → SetFsmId(500)`。
现在有官方模式表交叉验证：**该版本 `StandUp()` 请求的是锁定站立，而不是自主平衡；
`Start()` 请求的是常规运控，不能在悬空阶段把它当作仅摆站姿。**[S4][S9]

不自动遍历模式号、反复重试，或在不响应时释放服务。[S9]

`mode_pr` / `mode_machine` 不是平衡／阻尼 FSM。A2 当前只检查这两个原始字段及
profile 中的模式确认项，没有实时查询 FSM 来自动认定“锁定站立”；运行前后的 A1
查询结果和实际姿态仍需对照。遥控器按键不可靠时，不用随机试键来代替这一步。

### A1b：保持悬挂，用电脑试切阻尼与锁定站立

这一步按用户意愿安排，**不再属于 H1／read-only**：模式 RPC 虽然不是 `rt/lowcmd`
关节命令，也会使内置程序改变电机行为，锁定站立会让手脚摆姿态。
2026-09-15 已按此顺序执行，见 [本次模式切换记录](sessions/20260915_A1B.md)。

1. A1a 成功后，保持悬挂、脚离地，人避开关节摆动范围；还不启动 Arm SDK 输出。
2. 若读回零力矩，电脑单独请求 `Damp()`（1），然后重新查询；若已经是阻尼，无需重发。
   不为统一起点而先强制切零力矩。
3. 读回阻尼后，电脑单独请求 `StandUp()`（4），重新查询并等姿态稳定。
   若一开始已确认锁定站立，则不用绕回零力矩／阻尼再重走流程。
4. 保存请求前后 `fsm_id`、返回码和实际姿态变化。读回 4 且锁定站姿稳定后进入 A2；
   仍保持悬挂，不把“站姿摆好了”当成已经能平衡。
5. 返回错误、超时、模式没改变或读到未解释的模式时，停在当前有支撑状态并记录原值，
   现场核对服务／固件；不遍历编号、不改试 500／801，也不进 debug。

`g1_commissioning_query` 仍只查询；A1b 使用新增的 `g1_commissioning_mode_step`，
不把 setter 加进 H1 launcher 或 query。该工具只注册 FSM getter/setter，只允许
`0→1` 或 `1→4`，每个进程最多请求一次；已在目标模式则不重发。成功请求后只读观察
6 秒并重新查询。错误时停止，不重试、不自动回退模式，也不是急停工具。
官方 `g1_loco_client_example.cpp` 的序列化用法作为依据；没有直接运行其多选项入口。[S4]

明天能查到的是**当前** `fsm_id`、`fsm_mode`、`balance_mode` 和服务返回信息，
不是一键枚举所有支持模式。该版 PDF 将 `fsm_mode=0/1` 分别解释为站立／移动；
安装版 SDK 用 `balance_mode=0/1` 请求平衡站立／持续踏步。均须连同 FSM ID 和返回码
理解，不能只看一个数字就给整机贴“站立模式”标签；失败响应中的数值不作有效结果。[S4][S9]

### A2：悬挂、锁定站立，先测一个手臂关节

人的操作可以简化为：**保持悬挂，完成 A1a 查询、A1b 电脑切到锁定站立，姿态稳定，再运行 A2。**
电脑负责检查新鲜状态、实际目标和 profile，具体现有命令见第 8 节。当前工具仍会拒绝
未填写的模板；删除文档 A0 不会把这些软件检查自动改成通过。

1. **电脑尚不发手臂命令。** 沿用 A1b 已确认的锁定站立状态，不再重复切模式。
   若此后被改过模式，则重新查询并恢复本机已验证的锁定站立；机器人仍不靠自己平衡。
2. 姿态稳定后，先预览这次的角度目标。当前模板选择右肩 pitch；左臂五关节、腰 yaw
   和右臂其余四关节都使用各自启动时的实测角度作为固定 PD 目标。
3. 程序先读取当前姿态，准备所有可能受 Arm SDK 接管影响的有效上肢／腰部槽位，
   再平滑接入。**不能直接把目标写成全零，不能一开始就把 weight 跳到 1。**
   初次只用经审核的关节 PD 小幅动作，不接 MPC／逆动力学／额外前馈力矩。
4. 一个短测试只做：保持当前姿态 → 权重平滑接入 → 所选关节小幅慢动 → 回到本次起始
   姿态 → 平滑交还。下面列出当前模板的实际数值，现场使用的 profile 会在运行前打印／预览。
5. 你看程序和记录；带教看整机，不只看右手。记录目标／实测关节位置、weight、时间和
   全身视频，观察另一只手、腰和腿有没有意外变化。异常即停止，不加大增益／权重“试出来”。
6. 正常交还后观察内置运控接回时是否有突跳，再结束进程。确认没有遗留用户 publisher。
   不以“程序退出码为 0”代替交还成功；不在第一次动作时用拔网线／强杀进程测试应急。

### A2/A3/A4 到底给什么角度

`q0` 表示每次启动时读取的各关节实测角度；每个关节有自己的 `q0`，不是全零。

| 阶段 | 左臂 | 右臂 | 唯一腰关节 yaw | 实现状态 |
| --- | --- | --- | --- | --- |
| A2 当前模板 | 五关节 PD 目标固定在各自 q0 | 右肩 pitch：q0 → q0 + 0.02 rad → q0；其他四关节固定 q0 | PD 目标固定 q0 | 已有 |
| A3 当前实现 | 五关节从新鲜实测姿态平滑进入已审阅固定目标并 PD 保持 | 五关节同样进入已审阅固定目标并保持；不是 PID/MPC | 进入并保持 0 rad | FSM 500 实机执行通过；当前静态目标见下文，世界系瓶轴倾角左 0.532°、右 0.270° |
| A4 计划 | PD 保持固定姿态，不要求自然摆臂 | 独立控制；之后研究 PID/MPC | 计划保持固定 yaw 目标 | 无已配置的行走执行角度，尚未实现 |

A2 模板的 `offset_rad=0.02` 约为 1.15°；目标变化速度 `0.02 rad/s`，往外 1 秒、
停留 0.2 秒、返回 1 秒。所有 11 个有效槽的模板 PD 为 `kp=20, kd=1`，
`dq=0, tau_ff=0`。这描述的是当前模板和代码，不是已执行的实机参数。
仿真配置中的左臂五个固定角及腰 yaw 为零；**当前 A2 没有把仿真零位姿态搬过来**。[S8]

本机有效上肢／腰关节为左 5 + 右 5 + 腰 yaw 1，共 11 个。协议数组有 13 槽，
最后两个对应的 waist roll/pitch 无效并保持全零；这不表示本机有三个腰关节。
weight 在消息 motor slot 29，是共同接入权重。本目标允许双臂一起由用户给目标，
无需验证“左臂保留厂商自然摆臂”。[S5][S8]

### weight：官方示例与当前 A2 的实际区别

- 当前安装的官方 Arm5 示例：进入初始化循环就写 `weight=1`，同时把关节目标向零位
  插值；不是权重从零渐升。退出时先递减权重，最后再显式写零。这个固定版本以
  `0.2/s` 降 2 秒，约降到 0.6 后最后跳到零，不能把它描述为全程平滑降到零。[S5]
- 官方 XR 说明推荐接入和退出都渐变权重；示例代码有直接置 1 的写法，并说明其依赖
  目标限速／接近当前姿态的处理。两种写法不能混为同一段代码。[S3]
- **当前 A2 模板：2 秒 `0 → 0.1`，保持 0.1 完成往返，2 秒 `0.1 → 0`，
  总轨迹约 6.2 秒。** 现场后续经单独审核使用5°、weight=0.5配置并验证右肩响应；
  程序硬上限现为0.5，不能把配置直接改成1运行。[S8]
- **A3 是独立 profile／可执行文件：当前拍照配置 3 秒 `0 → 1`、保持 20 秒、3 秒 `1 → 0`。**
  该上限只对 A3 双臂加单腰保持开放，不改变 A2 的 0.5 硬上限；初次零位测试保持 5 秒。

因此当前 A2 只验证小权重接入、动作和退出。虽然左臂有固定 PD 目标，内置目标仍参与
混合，不能据此说已经实现完全接管或“锁死”。实际右肩运动也不保证恰好 1.15°。
要实现你最终的固定左臂、独立控制右臂，需要后续验证充分接管时的效果；A3/A4
不能通过直接复用这个静态低权重工具来宣称完成。

若锁定站立时接口不接受命令，先留存返回／状态和版本信息，向带教／Unitree确认。
不能以“手没动”为由进入 debug，也不让悬空的腿开始走来试接口。

## 4. 从吊着到着地：不要跳过自主平衡这一关

### A3：先让内置运控自己平衡，再叠加控臂

本节使用独立的 `g1_arm_balance_hold_execute`；2026-09-16 已完成零位及拍照姿态真机执行，
详见 [A3 现场记录](sessions/20260916_A3_HARDWARE.md)。

1. 先完成 A2 的交还并停止用户输出。涉及身体模式切换、调整吊架、重新布置线缆时，
   不继续运行用户手臂轨迹。
2. 在锁定站立／本机认可的准备状态下，由带教操作吊架，按对应说明使双脚触地。
   此时保留吊具支撑，锁定站立本身没有自主平衡。
3. 双脚触地后，先用本机已验证的方法进入常规运控。用户已在 2026-09-15 现场观察到
   机器人能原地自主平衡，但当时未保存软件 FSM 读回；下次必须先查询并得到 FSM 500。
   A3 程序不负责切模式，FSM 不是 500 就在 publisher 创建前拒绝。
4. A3 重新采集当前姿态，在 3 秒内将 PD 目标从实测姿态插值到本次审阅目标。
   当前静态世界系端平目标为双肩 pitch −4°、肩 roll 左 −1°/右 +1°、
   肘 pitch 左 −8.1°/右 −7.8°，其余手臂及唯一腰 yaw 为零。
   同时让全局 weight 从 0 增至 1；保持 20 秒，再保持目标并用 3 秒
   把 weight 退到 0。初始 `kp=20, kd=1`，`dq=0, tau_ff=0`；不复制仿真中的更高增益。
5. 运行期间内置运控继续负责腿部平衡，A3 不发走路速度、不调用模式 setter、
   `ReleaseMode` 或 `rt/lowcmd`。模式离开 500、L2+B、CRC／状态失联或 DDS 写入失败会
   停止正常轨迹；这仍是软件联锁，不是硬件急停认证。
6. A3 不再用反馈关节速度、跟踪误差、raw mode、统一 ±1.2 rad 角度范围或单次 deadline
   迟到作为中止条件；这些状态仍写入日志供事后查看。A2 原有条件不变。

#### A3 附加只读实验：确认 IMU yaw 参考是否在开机时建立

该实验只研究**姿态参考，尤其是 yaw 零点**；IMU 不提供平移位置，不能据此确定
“世界坐标系的位置原点”。官方示例把 `LowState.imu_state` 称为 pelvis IMU，
把 `rt/secondary_imu` 称为 torso IMU；既有 H1 trace 保存的是后者。官方代码确认
四元数顺序为 `[w,x,y,z]`、RPY 为 ZYX 欧拉角，但当前资料没有说明目标固件究竟在
开机、运控启动还是其他时刻重置 yaw。因此结论必须来自本机记录，不能预先填写。

1. 在场地标出 A/B/C/D 四个易辨方向；机器人朝 A 开机，网络可用后启动专用只读
   IMU 观察器。
2. 在 `FSM=0` 将整机转到 B，先记录明显非零 yaw，再保持 B 不动进入阻尼 1；
   比较切换前后稳定窗口。
3. 在阻尼 1 将整机转到 C，记录非零 yaw，再保持 C 不动进入锁定站立 4；
   比较切换前后稳定窗口。
4. 在锁定站立 4 将整机转到 D，记录非零 yaw，再保持 D 不动进入 500；
   稳定记录至少 10 秒。不启动 A3 publisher。
5. 比较 torso `rpy[2]`、四元数和陀螺仪，同时查看 waist yaw，避免把腰部相对转动误当作
   整机航向变化。每次都要“先转向并等稳定，再按模式键”。详细步骤见
   [IMU 零点验证指南](IMU_ZERO_REFERENCE_TEST.md)。

判读方式：某模式入口前的 yaw 已明显非零，进入后仍保留相近非零值，则该入口不重置。
若物理朝向确实未变却突然回到约 0，则支持该入口重置。单次试验不能排除持久化参考、
磁航向或漂移；结果含糊时保留未知。

这里通过的是“内置平衡 + 外部控臂”，不是“走路 + 控臂”。零速度时是否踏步由目标
运控决定，不能仅凭处于运动模式就写成已验证迈步。

### A4：只有条件具备，才验证实际迈步／短距离慢走

本节同样尚未实现。保持常规运控；腿部运动由内置程序完成，左臂目标仍固定，右臂受控。

1. **先不同时增加两个变量。** 手臂交还内置控制，由带教确认有限运动范围及防跌／
   线缆保护方式；没有适合移动的保护条件，就停在 A3。
2. 为满足“以后电脑给行走目标”的需求，先单独测试经过审核的 Loco 运动工具：
   先验证零速度／正常停止路径，再执行短时、低速、直线目标，最后主动发停止目标。
   速度、时长、最大位移和允许停车时间先由带教批准；第一次不加转向、不用持续无限运动。
3. SDK 有 `SetVelocity(vx, vy, omega, duration)` 和 `StopMove()`。其中停止是高层
   零速度请求，不是立即硬件急停；必须记录请求时刻和实物停止，不能以 RPC 成功返回
   代替“已停住”。不假设改成电脑控制就消除了你观察到的转向拖尾。[S4]
4. 这条单独运动及停止路径通过后，才在相同保护条件下叠加 A3 已通过的左臂保持／右臂动作。
   同时拍到脚确实迈步、手臂按用户目标运动，保存两类命令与状态的时间记录。
5. 若带教和目标说明允许原地踏步，也可用它替代短距离移动来验证并行性。但本地资料
   已标“持续踏步不推荐”，不能默认运行 `ContinuousGait(true)`；未获确认就不测。

带教用遥控器让机器人走、电脑控制手臂，也能证明“行走与控臂并行”。但这**不证明**
电脑的 Loco 指令／停止路径已通过；报告必须分开记。推荐优先完成电脑有限行走目标的
单独验证，再组合，避免以后仍不知道走路到底由谁触发。

### 正常收尾与异常中止不是同一个流程

- 正常结束动态测试：请求停止行走 → 确认实物稳定 → 手臂按已验证流程返回／交还 →
  停止用户程序 → 带教重新建立可靠支撑 → 按本机流程阻尼／关机。不能在没有支撑时
  直接把“切阻尼”当作正常停车。
- 碰撞风险、明显抖动、失衡、状态超时、错误模式、另一命令源介入、线缆／吊具异常：
  立即中止当前试验，由带教执行预先确认的应急处置，不等待程序完成回位。
  状态失效时，程序不能用旧姿态继续生成回位轨迹；进程死亡时更不能指望退出回调生效。
- 首次短时悬挂 A2 必须有经审核的失联处置方案和现场停止准备；未知的 watchdog／
  weight 行为按“旧输出可能持续”处理，不把自动停止当作依据，也不要求先拔线证明。
  无独立停止办法或已知保护失效时不开始输出。首次控臂通过不算崩溃／断网测试通过；
  若未来需要故障注入，另做悬挂、独立授权的试验，不在落地试验里突然拔线。

## 5. 为什么明天不顺带测全身 rt/lowcmd

它验证的是另一条路线：用户承担所有被驱动关节的控制，内置平衡／行走不能继续
照原样竞争输出；它不能证明 Arm SDK 协同能力，因此不属于本次最小目标。

本地 SDK 的 `g1_ankle_swing_example.cpp` 会先 `ReleaseMode()`，初始化全身关节 PD
和零位目标，再做踝部摆动；并非“只轻微动一下脚”。Arm SDK 原始示例也有零位初始化、
大幅抬双臂和 weight 直接置 1 的阶段，不能原样作为首测程序。[S5][S6]

只有之后明确要部署自己的腿部策略，或确认这台固件无法满足协同需求，才单独设计
lowcmd commissioning：重新完整悬挂、停止所有用户协同输出、按目标官方低层流程
进入 debug／释放内置运控、核对全身初始目标、限制与恢复方法。官方既有遥控器
debug 流程，也有 SDK `CheckMode/ReleaseMode` 路径；不预设它们在本机完全等价。[S2][S6]
本次不提供 lowcmd 执行命令，也不把“Arm SDK 没响应”作为自动改走 lowcmd 的条件。

### A1a：现场只读命令

当前真正存在的 H1 命令模板如下，仅用于 A1a，由现场确认网卡后执行。
2026-09-15 已执行的具体命令和结果见 [现场记录](sessions/20260915_A1A.md)：

```bash
env -u UNITREE_INGRESS_SESSION_NONCE \
  ./tools/realtime/run_hardware_state_inspection.sh <本次确认的有线网卡> \
  --duration-s 10 --inspect-samples 500 --group <本次唯一记录名>
```

在仓库根目录运行并先替换占位符。采够 500 条会提前结束，`10` 是等待上限，不保证
录足 10 秒。

A1a 使用的 query 会发送查询 RPC，但不发送控制命令。在本次有线网卡上查询当前 SDK 的 `sport`
服务，同时保存供离线预览使用的状态快照；零力矩／阻尼状态均可先做这一步：

```bash
/tmp/g1-commissioning-full/g1_commissioning_query \
  <本次确认的有线网卡> \
  --service-name sport \
  --permit-read-only-query A1_READ_ONLY_GETTERS \
  --state-wait-s 5 --rpc-timeout-s 2 \
  --output <新的A1查询报告.json> \
  --snapshot-output <新的A1状态快照.conf>
```

该程序原样保存 `version`、`mode_pr`、`mode_machine`、getter 返回码与原始值；
它明确写 `model_certified=false`、`mode_semantics_certified=false`。失败时不尝试 setter。
如果目标实际要求旧 `loco` 服务，本版本会拒绝，不现场猜测或改写服务名。

**这些命令不会完成 A1b 模式切换。** 只读工具没有 setter 参数。

### A1b：独立单次模式请求（有电机行为，不属于只读）

先按 [工具说明](../../tools/g1_commissioning/README.md) 构建独立 modes 目录，
启用 `G1_COMMISSIONING_BUILD_MODE_STEP`，保持 `G1_COMMISSIONING_BUILD_REAL_OUTPUT=OFF`。
现场保持悬挂、脚离地；先读取当前 FSM。每次只选择一个目标：先 `damp`，成功读回后
再单独选择 `locked-stand`，不能省去两次操作间的结果检查。

```bash
/tmp/g1-commissioning-modes/g1_commissioning_mode_step \
  <本次确认的有线网卡> \
  --target <damp或locked-stand> \
  --log <新的单次模式记录.jsonl> \
  --permit A1B_HOISTED_MODE_ONLY
```

模式请求可能使整机关节运动。程序只确认 FSM 读回与状态检查，不代替人观察真实站姿。
2026-09-15 实际使用的构建目录为 `/tmp/g1-a1b-mode-20260915/`；准确命令和结果见
[A1b 记录](sessions/20260915_A1B.md)。不把 `7301` 平衡子状态错误改成通过，亦不为消除它
进入常规运控。该错误在本次零力矩和锁定站立查询中均出现。

### A2：现场显式输出命令（当前禁止提前运行）

电脑端根据 A1 数据及本次动作，使用
[`site_profile.template`](../../tools/g1_commissioning/profiles/site_profile.template)
整理本次独立 profile。模板数值是软件示例，尚非已执行的实机参数；模板仍为 DRAFT，
不能把全部 `false` 自动改为 `true`。用 A1 快照先离线预览本次 profile：

```bash
/tmp/g1-commissioning-default/g1_arm_static_preview \
  --profile <本次经审阅的profile.conf> \
  --state <A1状态快照.conf> \
  --output <新的离线预览.jsonl>
```

本次 profile／预览准备好后，保持脚离地，确认 A1b 后仍处于锁定站立且姿态稳定，再运行：

```bash
/tmp/g1-commissioning-full/g1_arm_static_execute \
  <本次确认的有线网卡> \
  --profile <本次经审阅的profile.conf> \
  --log <新的A2日志.jsonl> \
  --session-label <本次唯一标签> \
  --permit-real-output A2_HOISTED_STATIC_ONLY
```

程序在创建 publisher 前还会要求人工输入 `EXECUTE <profile中的robot_id>`，并在输入后
重新收集连续的新鲜状态。任一 gate 失败即拒绝；日志存在时拒绝覆盖。正常轨迹结束或
状态新鲜时的 SIGINT 会渐变 weight 至零。CRC／时钟／mode／跟踪／deadline 等故障不再
沿旧状态回位，只尝试一条全零、weight=0 的 fault frame；**该尝试并不是已认证的硬件急停**。
进程崩溃不会执行清理回调；首次 A2 须审核独立人工处置和禁止自动恢复方案，
不要求事先完成固件失联行为实验，不据此假定固件安全。使用 v2 profile；旧字段
不自动迁移，交还是否平顺留到本次 A2 中观察记录。

### A3：落地常规运控中的双臂＋腰保持（零位及拍照姿态已执行）

再执行独立 A3 入口：

```bash

  <本次确认的有线网卡> \
  --profile <本次经审阅的A3-profile.conf> \
  --log <新的A3日志.jsonl> \
  --session-label <本次唯一标签> \
```

程序不会替你切换到 500，也不会发腿部／行走命令。创建 publisher 前仍要求输入

肩 roll 左 −1°/右 +1°、肘 pitch 左 −8.1°/右 −7.8°，其余手臂及腰 yaw 为零。
这是当前站立姿态下的静态世界系端平目标；初次全零 profile 仍可复现，也不是右臂 MPC。
瓶子中点的 [末端定义与姿态计算](ENDPOINT_FRAME.md) 与仿真 XML 共用几何。
