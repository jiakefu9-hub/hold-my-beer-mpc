## 从加速度到力矩：并非已经准确跟踪

完整 `[5,18)`，按主机时戳对齐、默认不平移命令：

| 右臂关节 | `tau_est − (FF＋重建PD)` RMSE / N·m | 实测区间加速度 − MPC 期望 RMSE / rad/s² |
| --- | ---: | ---: |
| 肩 pitch | 0.212 | 0.683 |
| 肩 roll | 0.127 | 1.953 |
| 肩 yaw | 0.109 | 0.804 |
| 肘 pitch | 0.208 | 0.868 |
| 腕 roll | 0.133 | 2.012 |

力矩误差中有明显固定偏差，不能把 0.1–0.2 N·m 一概说成“小得可以忽略”，尤其腕部请求本来就小。
`tau_est` 是机器人估计值，PD 是用主机反馈重建；均非独立测力标定。

更重要的是：8–18 s 肩 roll／腕 roll 的平均期望加速度仍为 **1.856／1.923 rad/s²**，
但它们的实测角度变化范围分别只有约 **0.013°／0.004°**，区间平均实测加速度接近零。
同一模型内的正动力学结果贴近期望，**实际关节却没有持续产生对应加速度**。
所以不能用“多候选正动力学通过”替代实机跟踪验证。

预先列出 0、3、6、12 ms 四种命令延迟假设，完整窗口肩 roll 的加速度 RMSE 仍为
1.953–1.960，腕 roll 为 2.010–2.012 rad/s²；这不是简单平移几毫秒就能消除的现象。
24 ms 的 dq 差分有噪声，不能把每个尖峰当真；但持续的期望值与几乎静止的角度也不能用噪声解释掉。
静摩擦／执行器死区、模型负载误差、内部力矩处理等均可能贡献，**本次不能区分或标定它们**。
当前不拟合固定倍数、不自动往力矩加偏置，更不改 PD 使对比组变差。

## 6 ms 时间结果

主窗口 2128 拍；计时口径包括采集、计算、构包、写入和工作日志入队，
不包含最后一条计时审计记录自身的入队开销。

| 项目 | 平均 / ms | P99 / ms | 最大 / ms |
| --- | ---: | ---: | ---: |
| 控制器计算 | 3.416 | 4.689 | 5.618 |
| 计算至写入前 | 3.793 | 5.213 | 6.563 |
| 完整工作 | 4.303 | 5.972 | 7.438 |
| 实际周期 | 6.107 | 11.743 | 12.444 |
| 写入时关节状态年龄 | 5.325 | 7.695 | 9.291 |
| 本地 DDS Write | 0.257 | 0.855 | 1.726 |

计入唤醒延迟后，**38/2128=1.786%** 错过 6 ms 截止时间，跳过 38 个时钟槽，
不是每拍硬实时通过。实际约 12 ms 的间隔与“计算没有超过 10 ms 拒绝线”并不矛盾：两者口径不同。
这也不是测得 DDS 单程／往返或电机内部响应延迟。

CPU 7 已为 performance，传输主线程实际所在 CPU 2 仍为 powersave；两者确实都是 FIFO 20。
下一次可将 CPU 2 也设为 performance 后保留同样计时，具体命令已补入程序文档。
这是减少主机抖动的候选措施，不宣称能消除全部超时；本轮没有修改主机设置。
目前没有证据要求立刻改成更长控制周期，更不能直接将原地计算时间当学习预测行走时间。
